# Radeon 780M 语音性能诊断（2026-10-31）

硬件为 Ryzen 7 H255（8 核 16 线程）、Radeon 780M 核显、32 GB RAM。CPU 使用独立的 PyTorch 2.9.1+cpu/MKL 环境；GPU 使用 PyTorch 2.14.0+rocm10.1.0/OpenBLAS 环境。模型、参考音频、CPUFast 源码版本相同，GPU 主模型为 FP16，CPU 为 FP32。这里比较的是现有两套完整运行环境，不是只改变设备的硬件微基准。

## 方法与边界

先退出桌宠及其语音子进程，再顺序运行诊断；未关闭用户其他桌面软件。每路 8 个 CPU 线程，固定 happy 参考和 seed 42，预热“你好。”，每次清除整句音频缓存，保留实际模型及参考特征缓存。四句公开测试文本：

1. 第46题。今天我们一起练习新的日语句子。
2. 第47题。先听一遍，然后试着用自己的话回答。
3. 第48题。答错也没有关系，我们可以慢慢练习。
4. 第49题。最后再回忆一下刚才学过的内容。

`diagnose_performance.py` 在独立进程加载真实桥接和模型，记录阶段、音频哈希与内存。计时含同步探针开销；阶段有嵌套，不能直接相加。`tensorMembership` 包含等待此前排队的 GPU 工作，并非纯数据复制耗时。生产 HTTP 路径另行验证，不能用直接函数调用代替真实服务验收。

## 隔离模型对照

| 路径 | 四句总耗时 | 条件 |
| --- | ---: | --- |
| CPU 两路并发 | 17.54 / 17.44 秒 | 各 8 线程，重复两轮 |
| GPU 单路串行，修复前 | 31.40–32.65 秒 | 热模型；较冷首轮 34.98 秒 |
| GPU 两路并发，修复前 | 32.25 / 33.45 秒 | 两模型驻留，共用一块核显 |
| GPU 两路先并发，修复前 | 39.98 / 32.60 秒 | 只预热招呼，再连续两轮 |
| GPU 单路，G2PW 修复前 | 31.85 秒 | 同一进程的第二轮 |
| GPU 单路，G2PW 修复后 | 23.29 / 23.42 秒 | 同一进程连续切换实现 |
| GPU 两路并发，G2PW 修复后 | 27.17 / 25.31 秒 | 新进程依次加载，各预热一句 |

之前记录的 GPU 两路 115.07 秒、CPU 13.92 秒是当时真实 HTTP 样本，保留原数据。115 秒未在上述隔离对照中稳定复现，不能将它解释为核显固定慢八倍；系统负载、服务线程和加载状态也应区分。

## 已证实的前端瓶颈与修复

中文多音字 G2PW 和文本 BERT 是不同的模型。之前只优化了 BERT，G2PW 仍使用 ROCm 环境的普通 CPU BLAS 路径。CPU 环境构建参数为 `BLAS_INFO=mkl`，ROCm 环境为 `BLAS_INFO=open`；不能以为换成 GPU Python 后，仍在 CPU 上的前端就保持原来的速度。

将 G2PW 线性层用同环境的 oneDNN 预打包后，四句 G2PW 总耗时从 **8.83 秒降至 0.44 / 0.38 秒**，总耗时下降约 **27%**。两轮优化结果的四个 WAV SHA-256 均与修复前对应音频相同。此结论限于测试句，未声称覆盖任意输入的逐比特一致性。

桥接仅对 CPUFast + ROCm 路径启用这项优化，保留原权重、词典和多音字选择。`runtime.json` 的 `rocm_cpu_g2pw: false` 可用于诊断对照，健康接口新增 `phonemeBackend: onednn`。CPU、NVIDIA 和上游引擎路径不受此开关影响。

## 仍然存在的限制

- **语义解码有大量串行等待。** CPUFast 解码循环每步通过 Python 判断 EOS。四句样本触发约 740 次张量成员判断；单路 GPU 中该范围约占语义阶段 18 秒中的 13 秒，CPU 对应成员判断约 0.025 秒。这说明大量计算和等待集中在逐步生成链路，不能把这 13 秒全部视为可删除的同步成本。实际代码见安装版本 `AR/models/t2s_model.py` 的 EOS 分支。
- **两个进程没有两块 GPU。** 两路并发时单个请求的语义阶段变慢，四句总体吞吐几乎不变。仅增加进程或 CPU 线程数不能消除同一核显上的串行依赖。
- **内存余量较小。** 修复前双 GPU 工作进程各约 6.2 GB 常驻、约 9.9 GB 私有提交，系统可用内存最低约 2 GB。共享 GPU 内存、进程工作集、私有提交不是同一指标，不能相加当作显存。加载阶段观察到页面读入，系统自动扩充了提交额度；双模型采样中也有大量页面读入为零的时刻，证据不足以认定持续磁盘换页就是 115 秒的直接原因。
- **清 GPU 缓存不是主因。** 同进程交替保留/释放缓存时，四句约 31–33 秒；`empty_cache()` 本身不到 1 毫秒，包含垃圾回收的清理阶段约 1 秒。没有据此删除生产缓存回收。

## 真实服务复核与未解决项

优化后双路真实 Electron 测试遇到预热超时；退出 Electron 后单独启动双路 HTTP 服务也出现第二路预热超时。因此不能只归咎于桌宠界面，也不能用隔离模型成功掩盖生产服务失败。未确认这两次超时和最早 115 秒样本是完全相同的原因。

进一步分别测试主线程、普通服务线程、在服务线程显式设置 CPU 线程数，四句为 27.40 / 25.51 / 23.83 秒；另一次从第一句起就在服务线程运行，预热 9.03 秒、四句 27.07 / 23.70 秒。各线程实际报告 8 个计算线程，没有复现几十倍的线程池开销。真实双进程服务与隔离调用的差异仍需继续定位，不据此增加线程或延长超时掩盖问题。

单路 GPU 与 CPU 双路都已在打包桌宠通过真实中文与日文合成、播放至结束和退出清理，各 4 项检查通过，零页面错误。两套运行方式先后测同四句真实 HTTP 请求、全部整句缓存 MISS：**GPU 单路 23.82 秒，CPU 双路 18.46 秒**。这两套环境精度不同，输出音频时长也略不同；是完整方案的比较，不是相同音频的纯硬件对照。

见 [GPU 单路 HTTP 数据](rocm-optimized-single-http-2026-10-31.json)、[GPU GUI 验收](rocm-optimized-single-gui-2026-10-31.json)、[CPU 双路 HTTP 对照](rocm-diagnosis-cpu-http-2026-10-31.json)、[CPU GUI 验收](rocm-diagnosis-cpu-gui-2026-10-31.json)。自动模式继续选择 CPU 两路；当前手动 GPU 推荐一路、8 个 CPU 线程。CPU 路径未被修改。

原始阶段数据与 WAV 哈希见 [诊断数据](gpu-diagnosis-2026-10-31.json)。这些测试没有使用用户对话、修改学习记录，也没有向云端发送内容。

[PyTorch 文档](https://docs.pytorch.org/docs/main/notes/cuda.html)说明 CPU 读取 GPU 结果需要同步；[empty_cache 文档](https://docs.pytorch.org/docs/main/generated/torch.cuda.memory.empty_cache.html)说明释放的是未占用的缓存块。这些用于解释机制，不能替代本机测量。

## 复现

```powershell
python -I -X utf8 -u integrations/gpt-sovits/diagnose_performance.py --root D:/go-project/vibecodingatempt/tts/gpt-sovits --device cuda --workers 2 --threads 8 --output test-results/gpu-diagnosis
```

`--parallel-first` 对照初次并发与第二轮；`--thread-test` 对照主线程、服务线程及服务线程显式线程数。`--g2pw-test` 只用于尚未启用 oneDNN 的基线：前两轮原实现、后两轮进程内转换。已经部署优化时，应先在独立诊断目录将 `rocm_cpu_g2pw` 设为 false；不要把两轮都已优化的数据当作 A/B。默认诊断不修改安装文件，不播放、不写用户聊天，不调用云端。
